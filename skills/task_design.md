# Skill: task_design — проектирование задач Jira

## Назначение

Преобразовать требования со статусом `OK` / `OK (допущение)` в бэклог Jira: Epic → User Story с критериями приёмки в Gherkin, с полной трассировкой REQ→TASK и учётом допущений этапа ревью.

## Вход / выход

- **Вход**: `artifacts/01_requirement_review.md` (требования со статусами + допущения).
- **Выход**: `artifacts/02_task_design.md` — бэклог (Epic + Stories + Tasks) и трассировочная матрица REQ→TASK.

## Правила

1. В работу берутся **только** требования со статусом `OK` / `OK (допущение)`. Требования `FAIL (блокер)` в задачи не превращаются — они в эскалациях.
2. Одна задача = одна пользовательская ценность. Не дробить по слоям (UI/сеть/логика) и не склеивать разные функции.
3. Формат User Story: `Как <роль>, я хочу <действие>, чтобы <ценность>`.
4. Каждый критерий приёмки (Acceptance Criteria, AC) — сценарий Gherkin: `Given … When … Then`. В каждой Story минимум: 1 позитивный AC, 1 негативный AC (если функция обрабатывает ошибки — обязательно).
5. Ограничения и особенности (`OS-N`), влияющие на пользовательское поведение, отражаются в AC соответствующих Story (а не в отдельных «задачах на дефект»).
6. Каждая задача содержит: ID (`ART-N`), тип (Epic/Story/Task), приоритет (по таблице ниже), оценку (Story Points: 1/2/3/5/8), ссылки на требования.
7. Приоритизация: `Highest` — ядро пути пользователя (лента, карточка, создание); `High` — интерактив (лайк, поиск, загрузка); `Medium` — удаление, просмотр изображения; `Low` — технический долг и улучшения.
8. Допущения этапа ревью фиксируются в AC явно (ссылкой на assumption) — чтобы при ответе заказчика легко найти затронутые задачи.

## Методики и паттерны

| Методика/паттерн | Применение |
|---|---|
| User Story pattern | Роль → действие → ценность |
| Gherkin (Given/When/Then) | Формат критериев приёмки; основа для последующих тест-кейсов |
| INVEST | Самопроверка каждой Story: Independent, Negotiable, Valuable, Estimable, Small, Testable |
| Vertical Slice | Задача режет функцию целиком (UI+данные), а не слой системы |
| Traceability matrix | REQ→TASK: требование без задачи — нарушение QG-2 |
| MoSCoW-приоритизация | Приоритеты Story на основе ценности для пути пользователя |
| Definition of Ready | Story берётся в работу только с AC, оценкой и трассировкой |

## Формат результата

```markdown
## Epic
| ID | Название | Описание | Покрывает |
|---|---|---|---|

## Stories
### ART-N. <Название>
- **User Story**: Как …, я хочу …, чтобы …
- **Приоритет**: High | **Оценка**: 3 SP
- **Трассировка**: FR-1, API-1, OS-1 | **Допущения**: A-1
- **AC**:
  - AC1 (позитивный): Given … When … Then …
  - AC2 (негативный): Given … When … Then …

## Трассировочная матрица REQ→TASK
| Требование | Статус | Задачи | Примечание |
|---|---|---|---|
```

## Few-shot пример

Вход: `FR-3 Лента артов (OK, допущение A-1: вероятность ошибки до 35%, клиент делает retry)` + `OS-1: случайная ошибка ~30% в GET /arts`.

Выход:

### ART-1. Лента артов
- **User Story**: Как посетитель галереи, я хочу видеть ленту всех артов, чтобы выбирать работы для просмотра.
- **Приоритет**: Highest | **Оценка**: 3 SP | **Трассировка**: FR-1, API-1, OS-1 | **Допущения**: A-1
- **AC**:
  - AC1 (позитивный): Given в галерее есть арты, When я открываю ленту, Then отображается список всех артов с названием, описанием, тегами и счётчиком лайков.
  - AC2 (негативный): Given запрос ленты вернул ошибку сервера (500), When ошибка получена, When приложение автоматически повторяет запрос, Then лента отображается без действия пользователя.

## Self-check (перед сохранением артефакта)

- [ ] Все требования `OK`/`OK (допущение)` покрыты задачами (матрица полная).
- [ ] 0 задач без AC; в каждой Story есть негативный AC.
- [ ] Все AC в Gherkin и проверяемы.
- [ ] Каждая задача проходит INVEST.
- [ ] Допущения этапа ревью отражены в AC и видны в матрице.
- [ ] Нет задач, не ссылающихся ни на одно требование.
