# Skill: test_design — тест-модель для TMS (TestRail)

## Назначение

Спроектировать тест-модель для TestRail по бэклогу этапа 2: тест-кейсы трёх обязательных классов — **позитивные**, **негативные**, **граничные** — с привязкой к задачам и критериям приёмки; сформировать матрицу покрытия AC→TEST.

## Вход / выход

- **Вход**: `artifacts/02_task_design.md` (Stories с AC, трассировка, допущения).
- **Выход**: `artifacts/03_test_design.md` — структура Suite/Section, тест-кейсы в формате TestRail, матрица покрытия AC→TEST, вердикт QG-3.

## Правила

1. Каждый тест-кейс привязан к задаче (`ART-N`) и критерию приёмки (`ACn`) — поле Refs; кейсов «в никуда» не существует.
2. Обязательные классы кейсов: **Positive** (штатный путь), **Negative** (ошибочные входы/состояния: неверные данные, отсутствующие объекты, сбои сервера), **Boundary** (граничные значения полей и состояний).
3. Граничные кейсы обязательны для любого поля с ограничением: длина строки L → тесты на `L-1, L, L+1`; числовой счётчик → `0, 1, максимум`; ID → существующий/несуществующий.
4. Особенности реализации `OS-N` — обязательные источники негативных кейсов: нестабильная лента (OS-1), null вместо 404 (OS-2), отсутствие валидации (OS-4), лимит 255 (из DR).
5. Формат кейса TestRail: `Title | Type | Priority | Preconditions | Steps | Expected | Refs`. Шаги нумерованы, один шаг = одно действие; Expected — наблюдаемый результат, проверяемый без интерпретаций.
6. Приоритет кейса наследует приоритет задачи; негативные кейсы на Critical-функции — не ниже High.
7. Недетерминированное поведение (случайная ошибка ленты) проверяется кейсом с политикой повтора: фиксируется «клиент обязан отобразить ленту за N повторов» (из допущения).
8. Один кейс — одна проверка. Комбинировать несвязанные проверки в одном кейсе запрещено.

## Методики и паттерны

| Методика/паттерн | Применение |
|---|---|
| Эквивалентное разбиение | Классы входов: валидные/невалидные данные полей арта, типы файлов, теги |
| Анализ граничных значений | Длины полей (0/1/254/255/256), счётчик лайков, ID записей |
| Таблица решений | Комбинации «поле заполнено/пусто» при создании арта |
| Паттерн «State transition» | Жизненный цикл арта: создан → с картинкой → лайкнут → удалён (проверки переходов и терминальных состояний) |
| Error-guessing (по OS-реестру) | Негативные кейсы из известных особенностей OS-1…OS-18 |
| Traceability matrix | AC→TEST: каждый AC покрыт ≥1 позитивным и ≥1 негативным кейсом |
| Паттерн «Retry-verification» | Для недетерминированных функций: проверка политики повтора клиента |

## Формат результата

```markdown
## Структура TestRail
Suite: ArtCase MVP → Sections по функциям (Лента, Карточка, Создание, …)

## Тест-кейсы
| ID | Title | Type | Priority | Preconditions | Steps | Expected | Refs |
|---|---|---|---|---|---|---|---|

## Матрица покрытия AC→TEST
| Задача/AC | Кейсы (позитив) | Кейсы (негатив) | Кейсы (граничные) |
|---|---|---|---|

## Вердикт QG-3: PASS / FAIL
```

## Few-shot пример

Вход: `ART-1 AC2: Given запрос ленты вернул 500, When получена ошибка, Then приложение повторяет запрос и лента отображается` (OS-1, допущение A-1).

Выход:

| ID | Title | Type | Priority | Preconditions | Steps | Expected | Refs |
|---|---|---|---|---|---|---|---|
| TC-7 | Лента: отображение после ошибки сервера (retry) | Negative | High | Приложение запущено; сервер доступен; в БД есть ≥1 арт | 1. Открыть ленту 2. Дождаться ответа сервера с ошибкой 500 (при необходимости повторить открытие до возникновения ошибки — вероятность ~30%) 3. Наблюдать поведение приложения | Лента отображается автоматически (повтор запроса), без ошибки пользователю | ART-1/AC2, OS-1, A-1 |

## Self-check (перед сохранением артефакта)

- [ ] Каждый AC покрыт ≥1 позитивным и ≥1 негативным кейсом (матрица заполнена).
- [ ] Для каждого поля с ограничением есть граничные кейсы (L-1, L, L+1).
- [ ] Каждый кейс имеет Refs (задача + AC) и проверяемый Expected.
- [ ] Каждый OS, влияющий на пользователя, покрыт хотя бы одним кейсом.
- [ ] Один кейс = одна проверка; нет кейсов с несколькими несвязанными проверками.
- [ ] Недетерминированные функции покрыты кейсом с retry-политикой.
