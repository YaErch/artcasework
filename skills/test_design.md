# Skill: test_design — тест-модель для TMS (Test IT)

## Назначение

Спроектировать тест-модель для Test IT по бэклогу этапа 2: тест-кейсы трёх обязательных классов — **позитивные**, **негативные**, **граничные** — с привязкой к задачам Jira и критериям приёмки; однотипные проверки по границам оформлять параметризованными кейсами (DDT); сформировать матрицу покрытия AC→TEST.

## Вход / выход

- **Вход**: `artifacts/02_task_design.md` (Stories с AC, трассировка, допущения).
- **Выход**: `artifacts/03_test_design.md` — структура (Проект → Разделы → Кейсы, тест-план), тест-кейсы в формате Test IT, матрица покрытия AC→TEST, вердикт QG-3.

## Правила

1. Каждый кейс привязан к задаче (`ART-N`) и критерию приёмки (`ACn`) через связи Jira/теги; кейсов «в никуда» не существует.
2. Обязательные классы кейсов (отражаются тегом): **Positive** (штатный путь), **Negative** (ошибочные входы/состояния: неверные данные, отсутствующие объекты, сбои сервера), **Boundary** (граничные значения полей и состояний).
3. Граничные кейсы обязательны для любого поля с ограничением: длина строки L → проверки `L-1, L, L+1`; числовой счётчик → `0, 1, максимум`; ID → существующий/несуществующий. Однородные границы оформляются **одним параметризованным кейсом**: в шагах используется плейсхолдер параметра, варианты перечисляются в таблице параметров (Test IT сам развернёт их в варианты при запуске).
4. Особенности реализации `OS-N` — обязательные источники негативных кейсов: нестабильная лента (OS-1), null вместо 404 (OS-2), отсутствие валидации (OS-4), лимит 255 (из DR).
5. Формат кейса Test IT: `Название | Класс (тег) | Приоритет | Предусловия | Шаги (Действие → Ожидаемый результат) | Постусловия (если нужны) | Параметры (для DDT) | Связи (ART-N/ACn, OS-N, A-N)`. Шаги нумерованы; у каждого шага — действие и проверяемый ожидаемый результат без интерпретаций.
6. Приоритет кейса наследует приоритет задачи (Highest бэклога → High в Test IT); негативные кейсы на крит-функции — не ниже High.
7. Статус кейса после self-check — «Ready to use» (до проверки — «Draft»).
8. Недетерминированное поведение (случайная ошибка ленты) проверяется кейсом с политикой повтора: фиксируется «клиент обязан отобразить ленту за N повторов» (из допущения).
9. Один кейс — одна проверка (параметризованные варианты одного условия — не нарушение). Комбинировать несвязанные проверки запрещено.

## Методики и паттерны

| Методика/паттерн | Применение |
|---|---|
| Эквивалентное разбиение | Классы входов: валидные/невалидные данные полей арта, типы файлов, теги |
| Анализ граничных значений | Длины полей (0/1/254/255/256), счётчик лайков, ID записей |
| Data-Driven Testing (параметры Test IT) | Границы длин и варианты поисковых запросов — один кейс, таблица параметров |
| Таблица решений | Комбинации «поле заполнено/пусто» при создании арта |
| Паттерн «State transition» | Жизненный цикл арта: создан → с картинкой → лайкнут → удалён |
| Error-guessing (по OS-реестру) | Негативные кейсы из известных особенностей OS-1…OS-18 |
| Traceability matrix | AC→TEST: каждый AC покрыт ≥1 позитивным и ≥1 негативным кейсом (учитывая DDT-варианты) |
| Паттерн «Retry-verification» | Для недетерминированных функций: проверка политики повтора клиента |

```markdown
## Структура Test IT

## Тест-кейсы
| ID | Название | Класс | Приоритет | Предусловия | Шаги (Действие → Ожидание) | Параметры | Связи |
|---|---|---|---|---|---|---|---|

## Матрица покрытия AC→TEST
| Задача/AC | Кейсы (позитив) | Кейсы (негатив) | Кейсы (граничные/DDT-варианты) |
|---|---|---|---|

## Вердикт QG-3: PASS / FAIL
```

Вход: `ART-3 AC2: Given запрос ленты вернул 500, When получена ошибка, Then приложение повторяет запрос и лента отображается` (OS-1, допущение A-1).

| TC-12 | Лента: отображение после ошибки сервера (retry) | Negative | High | Приложение запущено; сервер доступен; в БД ≥1 арт | 1. Открыть ленту → отправлен запрос GET /arts. 2. ## Self-check (перед сохранением артефакта)

- [ ] Каждый AC покрыт ≥1 позитивным и ≥1 негативным кейсом (матрица заполнена; DDT-варианты учтены).
- [ ] Для каждого поля с ограничением есть граничные проверки (L-1, L, L+1) — однородные собраны в параметризованный кейс.
- [ ] Каждый кейс имеет связи (задача + AC) и проверяемый ожидаемый результат каждого шага.
- [ ] Каждый OS, влияющий на пользователя, покрыт хотя бы одним кейсом.
- [ ] Один кейс = одна проверка; нет кейсов с несколькими несвязанными проверками.
- [ ] Недетерминированные функции покрыты кейсом с retry-политикой.
- [ ] Кейсы, прошедшие проверку, переведены в статус «Ready to use».
